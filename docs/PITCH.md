# 项目介绍（30 秒 / 3 分钟）

> 口播稿，不是书面报告。数字来自 `eval/MEASURED.md`，引用时带上口径。

---

## 30 秒版

这是一个企业内部 IT 服务台 Agent。

员工问工单、查设备、问制度，它会先判断：直接答、查一篇 SOP、多跳检索、调业务工具，还是拒绝。不是所有问题都走向量库。

真正难的是写操作。开权限、重置密码不能模型说了算，所以系统先生成审批单，人工确认后才执行，并且用会话绑定和幂等键防止重放。

检索 P@1 71.7%，端到端的路由和确认流都是 100%。

## 3 分钟版

### 0:00–0:30 问题

企业 IT 服务台有几个老问题：FAQ 命中率低、长尾问题全靠人工、工单和制度散在不同系统。

普通 RAG 项目一般有三个毛病：所有问题都走向量检索；写操作让模型直接调工具；答不出来就硬编。

我这个项目想解决的是：**从“能答”走到“敢执行”**。

### 0:30–1:10 方案

核心是一张 LangGraph 状态机，加一条自适应路由。

系统把员工问题分成五路：问候直接答；单条政策查一篇 SOP；多条件问题走多跳检索；查工单、查设备、开权限走工具；越界或证据不足就拒答。

有两个硬规则：只要出现 TKT 工单号或 AST 资产号，一定走工具，不信模型的路由判断；“帮我报修”才建单，“电脑蓝屏怎么办”只查排障 SOP，不强行开单。

### 1:10–1:50 检索

检索是 BM25 加 bge 向量，再用 RRF 融合，最后精排。

一个细节：BM25 不只索引正文，还把标题和小节标题一起索引。因为“VPN 怎么申请”这种短问句，正文里可能匹配不到，但小节标题“申请资格”能直接命中。这个改动把 P@1 从 58.3% 提到 68.3%。

多跳问题走 Self-RAG：检索、评分、不够就改写补检，最多三跳。

60 条检索集上，BM25 加向量加 RRF 的 P@1 是 71.7%，MRR 0.826。

### 1:50–2:30 写操作

这是项目最看重的部分。

四个写工具：建单、申请权限、重置密码、申请软件。它们都不直接改数据，只生成审批单。

流程是：规划器发现是写操作，先返回待确认；执行器没有确认就一个工具都不跑；用户点确认后，服务端校验这个动作确实属于当前会话、当前用户、且没过期；然后才执行，并按“工具名 + 参数”的指纹做幂等，重复请求直接回放上次结果。

高危权限，比如客户导出、付款、生产库，会自动加签信息安全组。

### 2:30–2:50 可靠性

所有外部依赖都能缺：没有 API Key 就走离线规则和抽取式回答；没有向量库用内存；没有精排用词法；Redis 挂了就退内存。

`/capabilities` 会报告实际生效的后端，避免“系统能跑但效果不对”却没人发现。

### 2:50–3:00 结果与边界

三套离线集：100 条意图、60 条检索、20 条端到端。端到端的拒答、路由、确认流都是 100%，关键词命中 87.5%。

边界也很清楚：`user_id` 还没做服务端认证，待确认操作存在进程内存，审批状态机只写了入口没有推进器。这些在 README 的“使用边界”里都写了。

一句话总结：**这个项目不是让模型多会答，而是让它在该查的时候查、该问的时候问、该拒的时候拒。**

## 讲的时候注意

- 30 秒版不要堆数字，只留 1–2 个。
- 3 分钟版按时间轴讲，每段只讲一个点，别在检索段展开代码。
- 被追问“100% 怎么来的”，直接说：规则加 FAQ 兜底，集合是自建的，存在过拟合；纯覆盖层是 90%。
- 被追问“写操作真的安全吗”，先讲四层，再主动说内存确认表的局限，可信度更高。
